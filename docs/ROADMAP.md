## MVP

- [x] **0. Scaffolding**: Go module, Angular 22 workspace (`/web`), dev proxy, embedded SPA serving, `/api/health`, multi-stage Dockerfile, compose example. *Done when:* `docker compose up` serves the empty Angular app with a working health call. ✅ Binary + embedded SPA verified locally; the Docker image is built by CI and runs on the home server since step 7.
- [x] **1. Container inventory**: `internal/docker`, `GET /api/containers`, dashboard listing containers grouped by Compose stack. *Done when:* the dashboard shows your real containers. ✅ Verified against a snapshot of the home server (24 containers, 10 stacks) from `scripts/snapshot.sh`. Live socket mode is covered by tests against a fake Engine API.
- [x] **2. Versions & registries**: `internal/version` (parse, variants, compare, classify) with thorough unit tests on real-world tags. `internal/registry` (tags, digest HEAD, auth for Hub/GHCR/Quay/lscr). `internal/resolve` running-version chain. *Done when:* every container shows running → latest + update class + how the version was found. ✅ Against the home snapshot: 24 images checked in ~9 s, 11 updates found; 21/24 exact running versions (tag, label, digest), the rest are a nightly build, an unlabeled floating tag, and a rebuilt official image (fixed by `*_VERSION` once the snapshot is re-taken). Check runs: at startup and via "Check now", results in memory until step 3.
- [x] **3. Storage & scheduling**: SQLite + migrations, tag cache, check runs, scheduler, `POST /api/checks`, "Check now" button. *Done when:* results survive restarts and refresh on schedule. ✅ Verified end to end: startup check, restart shows all 24 results instantly without re-checking, schedule fires on its own using the persisted tag cache.
- [x] **4. Changelogs**: `internal/source` (repo resolution), GitHub + GitLab releases, CHANGELOG.md fallback, compare/release links, detail page with rendered notes. *Done when:* clicking a container shows the releases between running and latest. ✅ Against the home snapshot: 11 updates prefetched with 11 GitHub requests, detail pages answer in ~50 ms; ranges, compare links, CHANGELOG fallback, no-notes and unknown-version cases checked visually.
- [x] **5. Breaking-change analysis**: heuristics, per-release flags, highlighted lines, level badges + filters on the dashboard. Also: **phone-width list view** stacks each row (icon + name, then version change + update badge; image line dropped), because today Version/Update scroll off-screen below ~640px. Also cap very long release notes on the detail page with a "show more" (one mealie release is 15 000 px tall on a phone). ✅ Tuned on ~900 stored real releases (9 repos): bare "breaking"/"migrate"/"removed" were too noisy, so patterns are phrase-level with negations, sections inherit their heading's level, and lines already in the running release's notes (ignoring numbers and links) don't count. Home snapshot: 5 breaking (3 major jumps, Home Assistant `(breaking-change)` PRs, Traefik 3.6.14's Chain middleware change), Vaultwarden attention (its "Upgrade notes"), the rest calm. Checked in Chrome + Firefox, both themes, 1280 and 390 px.
- [x] **6. Rules**: ignore / pin / allow-major / prerelease / tag-pattern / repo override via labels + config file. ✅ `internal/rules` merges labels > `containers:` > `images:` entries of a `config.yaml` that's re-read each check; invalid values are skipped and shown, a bad file is reported while the last good one stays in use. Pins and `allow-major=false` keep the held-back version visible ("18.6-alpine held back by pin 16"); ignored containers make no outside calls and sit in a collapsed group at the bottom; results go stale when a container's rules change. Pre-releases now order by stage and number (`rc.2` < `rc.10`). Checked against the home snapshot with test labels + config (pins on postgres and Traefik, majors off on mongo, two ignored, two invalid rules, a config repo) in Chrome + Firefox, both themes, 1280 and 390 px. Built by four agents in parallel against fixed contracts (rules, resolve, wiring, frontend).
- [x] **7. Deploy to the home server**: build the image, run with socket-proxy, tune against your ~20 real containers (fix version-detection misses). ✅ GitHub Actions runs vet, gofmt and all tests, then builds the image and pushes it to GHCR (`latest` + `sha-<commit>`); the first build of the Dockerfile worked as-is. Runs in a stack behind a reverse proxy with its own socket proxy (`v0.5.0`, only `CONTAINERS=1 IMAGES=1`, on an internal network), a named data volume and `tidemark.ignore` on itself (its image is private). Healthy, first check 26 containers in ~10 s. Tuning against a fresh snapshot: 23 of 24 checked containers have an exact running version (9 tag, 10 label, 2 digest, 1 `*_VERSION`: postgres `16-alpine` → 16.15); the one left is mealie `nightly`, which led to **channel tags**: `nightly`/`dev`/`edge` are no longer compared with the newest stable release (shown as a quiet line), only a new build counts, and there's no verdict from stable notes. Also: the summary line counts ignored containers and the gauge count explains what it counts. Known gap: mongo and postgres have no notes (their GitHub repos have no releases); parked below.

## Between MVP and step 8

From the owner's notes after the MVP. One PR each; the release comes last so v1.0.0 includes the rest.

- [x] **H1. License**: MIT. ✅ `LICENSE`, a README section (the selfh.st icons keep CC BY 4.0), `license` in `web/package.json`; the image's licence label comes from the repo via `docker/metadata-action`.
- [x] **H2. CI tidy-up**: skip docs-only changes (`*.md`, `docs/**`, `LICENSE`), cancel superseded PR runs. ✅ `paths-ignore` on both triggers and a `concurrency` group that cancels only on PRs (every merge to main still gets its image); the roadmap PR merged right after it started no run on main.
- [ ] **H3. Angular restructure**: one folder per component (`name.ts` / `.html` / `.css` / `.spec.ts`), always split, also for small pieces; `ui/` keeps its name (it is the design system) and pages get the same layout. No behaviour or visual change. ✅ Every component has its own folder (`.html` always, `.css` only with styles, so `skeleton` and `markdown` keep `template: ''`); multi-component files were split (`status.ts` → `update-class/`, `level/`, `version-diff/`; `update-info.ts` → four folders + `dashboard/format.ts`; `container-table.ts` → `container-table/` + `column-bar/`); services sit next to their component (`theme-switch/theme.ts`, `toaster/toasts.ts`); `ui.spec.ts` was split into per-component specs. The `ui` barrel exports the same names. All 85 tests unchanged and green; screenshots in Chrome + Firefox, both themes, 1280 and 390 px match the previous run pixel for pixel apart from the animated waves. Done by two agents in parallel (ui/, pages).
- [ ] **H4. Visible check failures**: today the reason sits in a tooltip on "refresh failed" / "check failed" (not discoverable) and in a muted line under "Checked" on the detail page (easy to miss). Make the reason visible without hovering and readable (rate limit, auth denied, not found, timeout instead of raw Go errors). The owner had two containers fail on scheduled refreshes; a manual check cleared them, so capture the real errors after the next one.
- [ ] **H5. Releases + v1.0.0**: a git tag `v1.2.3` publishes `1.2.3`, `1.2`, `1` and `latest` plus a GitHub Release with generated notes, and builds with that version; merges to `main` only test (the leaner option, chosen after looking at the free tier: about 3 billed minutes per run against 2,000 a month; GHCR storage is currently free). The owner pulls `:latest` (or `:1`) after a release. Plus a cleanup of old image versions after each release (not on a schedule: the owner doesn't develop this full time). Pipeline built: single-manifest images (provenance/SBOM off) so untagged versions can be pruned safely; `cleanup.yml` keeps every release version, the newest 20 others and anything younger than 14 days (the selection filter was tested locally on sample versions). Stale merged branches deleted, and GitHub now deletes a PR's branch on merge. Left: tag v1.0.0 after the merge, check the release run, and run the cleanup once as a dry run.

## After MVP

- [ ] **8. Reviewed / snooze state + update history**
- [ ] **9. Telegram notifications** (notifier interface, new-findings-only diffing, test button)
- [ ] **10. AI changelog summary** (opt-in, cached, verdict can only raise the level)
- [ ] **11. Gated one-click update** (gates, floating-tag check, pull/recreate, healthcheck, rollback)
- [ ] **12. Stats** (later; brainstorm with the owner first, builds on step 8's history). Ideas so far:
  - *Behind:* how long each container has been behind (age of the running version vs. the latest), updates per container and stack over time, an up-to-date ratio over time (the tide as a history chart).
  - *Upstream:* release cadence per image/repo, breaking vs. calm releases per repo, biggest version jumps.
  - *Check health:* failures per container and reason, check durations, registry and GitHub requests, GitHub quota used.
  - *Lifetime (for fun):* containers ever tracked, updates applied (running version changed), breaking changes caught, release notes read, check runs, longest-behind container ever, fastest update after a release, longest fully-up-to-date streak, mean time to update, Tidemark's own uptime.
